# Corrected Phase 2: Trajectory-Diverse CCPR Versus Independent Proposal

**PHASE 2 FAIL - CCPR NOT SUPERIOR, MOVE TO DSQD.**

The mandatory breadth/generalization gate failed: **one**, not two, newly refined
CCPR specialists survived fresh DEV, representing only sell top-up. This is not
a claim that CONTROL won every metric. CCPR found BUILD repairs faster and its

positive results do not establish the required multi-effect discovery method.

it was not implemented. No frontier, champion promotion, packaging, push or

## Fair Frozen Comparison

- Both arms have the same 25 initial programs: six windows times four bodies,
  plus the Phase-2D wool-price <=241 reference. Starts normally last 48 turns;
  the 695 window is capped at the remaining 24 turns.
- Both have at most seven evaluations per lineage. CCPR uses the existing
  WHEN-first/STOP proposer, at most six refinements and two predicate clauses.
  It does not learn a new BODY, feature, REACT state or runtime abstraction.
- CONTROL's entire proposal list is saved before the first candidate outcome.
  It interleaves independent duration changes with one- and two-clause gates
  from the same unlabeled quartile vocabulary. Gates need broad legal-observation
  support, at least two retained roots and both seats; coverage then semantic
  hash breaks ties. Outcome changes cannot change this list, as tested.
- Both stop on the first group-safe useful incumbent, zero terminal effect,
  proposal exhaustion or the common evaluation cap. There is no quota padding.
  Consequently realized costs differ. This is equal opportunity/caps, not a
  falsely asserted equality of every executed continuation.
- The unchanged Phase-2D ranking prioritizes protected transitions, negative
  seed-group count and worst-group margin before aggregate value. Eligibility
  additionally requires no negative seed-group net, multiple positive seeds and
  both-seat support, separately on discovery and guard.
- Before guard, each arm freezes up to eight effect representatives. First
  retain the best of each available action mechanism, then fill by rank.
  Empirically equal BUILD effects are deduplicated, not asserted equivalent
  universally. The reference's BUILD effects matched the simpler ungated 359
  top-up; it did not receive an extra independent DEV query after that body failed.
- Guard rejects without replacements or new predicates. Only guard survivors
  reach legal full-game BUILD and DEV. Both arms use identical compiler/runtime
  semantics and exact PARENT fallback. Even identical programs in the two arms
  are reevaluated and charged to each arm; neither receives free cached outcomes.

## Decision And Limits

The data show genuine **metric-level advantages** for CCPR: more safe useful
BUILD candidates at exactly matched prefix cost, less discovery work overall,
earlier discovery of the eventual survivor, and 10 versus 1 safe DEV T->W.
Do not interpret this failure as evidence that CCPR has no value or that
independent proposal dominates it numerically.

Nevertheless, the required primary-method validation fails: only **one CCPR
specialist in one effect family** survives, rather than at least two across two
families. The frozen conservative footprint comparison reports no material
advantage because the surviving CCPR repair runs up to 48 turns versus CONTROL's
16 and survivor/effect counts tie; this does not erase the favorable efficiency
measurements. The mandatory breadth failure is decisive regardless of that
additional comparison rule.

Dominant bottleneck: **generalization breadth**. A useful top-up repair survives,
but the independently guarded CCPR ordering repair still regresses on fresh DEV;
worker-deposit and liquidation hypotheses supply no replacement capability.
Six independent seeds per window/panel are still a small sample, and the internal
league remains narrow. This is a bounded failure of the required validation bar,
not a universal impossibility proof about counterexample-guided synthesis.

Per the requested stopping rule, do not tune more predicates or scale this
campaign. Recommend the planned bounded **DSQD** comparison using the validated
fork infrastructure. **No DSQD or Phase 3 implementation is part of this commit.**
