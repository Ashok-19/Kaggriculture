# 1. Ultimate objective

The project objective is not incremental leaderboard improvement. The objective is to build the strongest possible deterministic Kaggriculture agent and finish **#1**, with gold/prize-money performance.

The internal optimization target remains:

- 100% win rate on all known current top agents where executable/frozen evaluation is available;
- 100% win rate on strong historical agents;
- 100% win rate on strong public executable agents;
- 100% win rate against historical ReCurSiON agents;
- zero avoidable regression against already-solved strategic regimes;
- continual discovery of new adversarial regimes until no meaningful known weakness remains.

The 100% target is an optimization direction, not a promise of mathematical certainty against all unknown future policies.

The final submitted policy must remain **deterministic**.

# 2. Non-negotiable architectural rules

These rules override convenience.

## 2.1 BKG4/Bonsai remains the final runtime backbone

The submitted policy is a deterministic Bonsai/BKG4 program. Offline tools may use search, planning, program synthesis, learned surrogates, adversarial populations, optimization, or other expensive methods, but their output must compile back into ordinary deterministic BKG4 behavior.

Do not replace the final agent with pure RL, BC, an opaque neural policy, or a runtime planner unless the user explicitly changes the architecture.

## 2.2 Specialists are first-class; global strategy optimality is not the objective

Do not search for one route that dominates every opponent/regime.

Bonsai exists because different strategies are optimal in different public causal regimes. A specialist may be extremely strong in one regime and harmful elsewhere. The requirement is to discover the capability and synthesize a gate that activates it only where justified.

Therefore:

`specialist quality + correct public-state routing + safe composition`

is the core strategy.

## 2.3 Runtime routing must be strategy/mechanic/state based, never identity based

Offline labels may know which source opponent produced a case. Runtime BKG4 logic must never branch on:

- opponent username/team name;
- submission ID;
- episode ID;
- replay/tape ID;
- exact seed as identity;
- hidden future information;
- any private information unavailable in the legal observation/runtime state.

Allowed gates must express legal causal state: shops, market, capital, production, labor, timing, farm state, derived economic conditions, finite causal memory where genuinely needed, etc.

## 2.4 CUDA is the heavy-search engine

All large-scale game evaluation/search must use CUDA.

Use CUDA for:

- regret search;
- macro search;
- beam/evolution/MCTS/LNS;
- adversarial-policy search;
- PSRO payoff evaluation;
- CEGIS counterexample campaigns;
- engine-semantic microgames;
- large regression panels;
- corpus/ranker work if it is resumed later.

Avoid heavy CPU/RAM workloads.

CPU C++ is for bounded reference/parity/sanity where needed.

The official Python engine is not a large-scale search engine. Before actual submission/champion release, run the required bounded official Python canary (normally 64/128 games) to confirm the C++/CUDA result still holds in the official execution path.

## 2.5 CPU/CUDA/BKG4 semantics must remain exact

Any strategy accepted from CUDA must translate exactly to CPU C++/BKG4 semantics.

Never introduce a CUDA-only policy behavior.

## 2.6 Shared-market changes require adversarial accounting

For every market idea ask:

> Does this improve our private outcome, or does it also improve the opponent equally/more through the shared market?

Do not credit a strategy merely because it changes shared prices in a direction that looks favorable.

## 2.7 Major gains only

Do not spend strategic effort on cosmetic refactors, tiny average-margin changes, gratuitous abstractions, or infrastructure that does not materially improve capability discovery, routing, composition, robustness, or throughput.

# 3. Strategic thesis

The deep-research conclusion and P0.1 experiment jointly establish the current thesis:

> **The dominant bottleneck is not raw Bonsai capacity and not primarily ranker capacity. It is discovering genuinely new coherent capabilities outside the current local edit manifold, then synthesizing safe public-state initiation/termination logic and composing those capabilities without regression.**

The intended long-term architecture is therefore not:

`generate millions of local edits → neural ranker → choose top edit → repeat`

as the central improvement engine.

The intended architecture is:

`current BKG4`
→ `adversarially discover weakness`
→ `locate high-regret state/window`
→ `deep CUDA planning / macro search`
→ `discover superior coherent continuation`
→ `compile/synthesize bounded macro/subtree`
→ `CEGIS initiation/termination/abort/recovery logic`
→ `exact CUDA validation`
→ `automatic Bonsai composition`
→ `adversarial regression / PSRO attack`
→ `stronger BKG4`
→ repeat.

The final program becomes an accumulated deterministic strategic memory containing many verified specialists.

# 4. Research foundations that guide the plan

The project should borrow ideas, not blindly copy architectures, from several research families.

## 4.1 Regret-Guided Search Control / Go-Exploit

Core lesson: do not spend expensive planning uniformly from the initial state. Focus search on states where the current policy leaves large recoverable value on the table.

Project translation:

- maintain a regret-state archive;
- restart planning around hard losses and fragile wins;
- prioritize by loss severity, recoverability, recurrence, causal novelty, and estimated regret;
- search coherent continuations from those checkpoints.

## 4.2 Expert Iteration

Core lesson: an expensive search teacher can produce stronger decisions than the deployed policy, while a cheaper apprentice executes the learned result.

Project translation:

- CUDA planning/search is the teacher;
- Bonsai program synthesis is the apprentice/distillation target;
- final runtime stays deterministic and cheap.

## 4.3 Hierarchical Programmatic RL / hierarchical program synthesis

Core lesson: flat local program mutations can be trapped inside a restricted behavior manifold, while coherent hierarchical programs/macros can reach qualitatively new policies.

Project translation:

- first-class bounded route fragments;
- multi-stage macros;
- phase machines;
- recovery blocks;
- coherent 20–100-node subtree replacement when evidence justifies it.

## 4.4 CEGIS / reactive synthesis / initiation-set learning

Core lesson: a good capability is not enough; its safe applicability region must be learned against counterexamples.

Project translation:

`candidate macro`
→ positive states
→ harmful counterexample
→ refine gate
→ repeat
until a causal initiation region transfers independently or the macro is rejected.

## 4.5 PSRO / double-oracle / adversarial policy populations

Core lesson: do not rely on one external opponent distribution. Continuously search for approximate best responses against the current policy/population.

Project translation:

- private deterministic policy league;
- evolve/search new exploiters;
- use payoff vectors for strategic diversity;
- feed discovered losses back into regret search and synthesis.

These research ideas are guides. They do not justify unnecessary generic frameworks.

# 7. Immediate priority — Stage 1 synthesizer proof

This is the **next task**. Nothing else outranks it unless the user explicitly redirects the project.

## Goal

Turn a P0.1 planning-discovered coherent continuation such as route435 into a **first-class bounded Bonsai macro/subtree specialist** with an independently validated public-state initiation set.

This stage is intentionally narrow.

Do not build the entire ultimate synthesizer yet.

## 7.1 Build bounded macro/subtree representation

The representation must be capable of encoding a coherent route fragment as a single strategic object rather than dozens of independent local edits.

Minimum requirements:

- explicit bounded activation start/continuation semantics;
- deterministic duration or termination behavior;
- coherent worker + market coordination;
- exact CPU/CUDA materialization;
- semantic identity suitable for dedup/evidence;
- no opponent identity;
- no tape/seed identity;
- no hidden future dependence;
- compatible with BKG4/Bonsai integration;
- minimal ABI/VM disturbance; avoid ABI change unless truly necessary.

Prefer the smallest extension that can represent the proven route435 capability.

Do not design a universal DSL before this first capability is integrated.

## 7.2 Initiation-set CEGIS

Given a proven macro, automatically synthesize the public causal region where the macro is useful/safe.

The initial candidate feature set should prioritize mechanistic state such as:

- visible shop multiset/order/regime;
- current step/day/remaining horizon;
- own and opponent public money;
- own/opponent hires and visible labor state;
- land ownership/expansion state;
- visible plant/animal/structure counts;
- public market inventory/prices;
- own legal private inventory where runtime permits;
- production pressure;
- current route/commitment phase;
- simple derived economic predicates where necessary.

Do not default to arbitrary exact scalar fingerprints.

### CEGIS loop

1. Start from known positive route435 states.
2. Generate a small candidate public-state gate.
3. Evaluate macro under that gate on discovery cases with CUDA.
4. Find harmful activations / W→L counterexamples.
5. Add those counterexamples to the synthesis set.
6. Refine the gate.
7. Repeat until either:
   - a compact causal gate achieves independent transfer with no protected W→L, or
   - evidence shows no clean causal initiation region exists.
8. If no clean gate exists, reject route435 as a production specialist rather than overfit it.

The search objective is lexicographic:

1. runtime/semantic validity;
2. zero protected W→L;
3. retain L→W flips;
4. improve worst-group win floor;
5. improve lower-tail margin;
6. only then average margin.

## 7.3 Stage 1 transfer requirements

Do not accept a gate solely because it selects the original positive cases.

Require:

- independent tapes/episodes;
- both seats when available;
- multiple strategy families/regimes where the same causal condition recurs;
- protected historical/current/self-history regression panels;
- no identity/tape/seed leakage;
- exact CUDA evidence;
- bounded CPU C++ semantic sanity/parity where the new representation touches materialization semantics.

A narrow but real causal specialist is acceptable. A broad but mixed-sign gate is not.

## 7.4 Stage 1 success criterion

Stage 1 is complete only if at least one planning-discovered macro is transformed into a reusable BKG4 specialist that:

- retains at least one meaningful independent L→W;
- activates on multiple independent legal states;
- has zero protected W→L on the promotion suite;
- translates exactly through CPU/CUDA/BKG4 semantics;
- is represented as a reusable bounded macro/subtree rather than a hard-coded tape patch.

If route435 fails CEGIS, use that failure evidence to refine the macro representation/search and test the next strongest planning-discovered macro. Do not lower the validation standard.

# 8. Stage 2 — repeat regret-guided capability discovery

Once the first macro/subtree + CEGIS integration works end-to-end, generalize the process.

## 8.1 Maintain a regret-state archive

Archive high-value checkpoints from:

- known losses;
- fragile wins;
- large negative-margin states;
- states where adversarial best responses diverge;
- specialist boundary failures;
- composition conflict states;
- engine-mechanic anomalies;
- new current-meta losses.

Each archive entry should record:

- reproducible game/tape evidence;
- legal state/checkpoint;
- current BKG4 outcome;
- seat;
- strategic/economic regime descriptors;
- known local search headroom;
- known planner headroom;
- whether the failure is recoverable after this checkpoint;
- discovered candidate macro families;
- unresolved reason.

Prioritize search approximately by:

`loss severity × recoverability × regret × recurrence × novelty`.

Do not search every state equally.

## 8.2 Planning horizons

Search coherent windows at horizons such as:

- 24;
- 48;
- 72;
- longer where evidence supports it.

P0.1 proved that useful windows may lie outside fixed grids. Therefore horizon/checkpoint selection must adapt to evidence.

## 8.3 Macro vocabulary should expand only from evidence

Useful families may include:

- capital expansion sequences;
- worker scheduling/assignment macros;
- land expansion;
- crop-system transitions;
- animal-system transitions;
- shop-conditioned production;
- inventory recovery;
- EOD recovery;
- market accumulation/liquidation;
- option-preserving openings;
- delayed commitment;
- endgame conversion;
- engine-semantic tactics;
- recovery routes;
- coordinated multi-stage sequences.

Do not add a macro family because a paper mentions it. Add it when hard-loss evidence or engine analysis demonstrates plausible headroom.

## 8.4 Search methods

Use the simplest effective method per capability:

- hierarchical enumeration;
- beam search;
- MCTS;
- LNS;
- evolutionary search;
- cross-entropy search;
- route recombination;
- reduced dynamic programming;
- exact microgame enumeration.

Do not build one giant generic planner if small specialized searchers solve the target subproblems better.

## 8.5 Distillation requirement

A planner-discovered action sequence is not itself a final strategy.

For every winning continuation determine:

- what causal strategic motif generated the gain;
- whether the motif recurs;
- what public state predicts applicability;
- whether a compact macro/subtree can reproduce it;
- what abort/recovery conditions are eventually required.

Exact future-dependent tape strings are rejected.

# 9. Stage 3 — specialist library and capability taxonomy

As successful macro specialists accumulate, maintain a first-class specialist library.

Each specialist should contain or reference:

- parent lineage;
- semantic identity;
- macro/subtree program;
- initiation condition;
- normal termination;
- abort condition if needed;
- recovery/fallback if needed;
- activation evidence;
- L→W / W→L evidence;
- margin effect distribution;
- supported economic/mechanic regimes;
- incompatible specialists/resources;
- source search lineage;
- counterexamples used by CEGIS;
- regression panels passed.

## 9.1 Strategic diversity, not syntax diversity

Two specialists that look different syntactically but beat/fail against the same regimes may be redundant.

Track strategic response vectors against the private policy league/current evaluation universe.

Prefer repertoire growth that adds new solved regimes.

## 9.2 Never delete a useful specialist merely because it is globally harmful

If the specialist is strongly beneficial in a coherent safely detectable regime, keep it and solve routing.

Only reject when:

- no legal causal initiation region can separate positive from harmful behavior;
- the effect is hindsight/future dependent;
- the same capability is dominated by a simpler safer specialist;
- implementation cost exceeds strategic value.

# 10. Stage 4 — automatic Bonsai composition

This becomes a priority only after several independently validated macro specialists exist.

The composition system must automatically decide how specialists coexist in one BKG4 tree.

## 10.1 Composition relations

Represent relationships such as:

- mutually exclusive;
- one preempts another;
- one can nest inside another;
- one requires a specific parent phase;
- one requires recovery after abort;
- shared blackboard/state resource conflict;
- shared market interaction conflict;
- same lane with priority;
- fallback relationships.

## 10.2 Composition search objective

Never assume individually good specialists combine safely.

Evaluate compositions exactly:

`parent + A`
`parent + B`
`parent + A + B`
`parent + A + C`
...

Use CUDA to search promising compositions and reject interference.

Lexicographic objective remains:

1. validity/semantic parity;
2. zero protected W→L;
3. maximize new L→W;
4. maximize worst-regime win floor;
5. lower-tail robustness;
6. average margin.

## 10.3 Tree size

Do not constrain the tree to the historical ~345 nodes.

The architecture supports ~65K nodes. If thousands or tens of thousands of nodes are justified by distinct validated strategic regimes, use them.

Tree size is a resource, not an objective.

Monitor runtime/hot-path cost, but do not reject strategically valuable growth merely because the tree is larger.

# 11. Stage 5 — programmatic adversarial / PSRO league

The project must become increasingly independent from fresh leaderboard replay discovery.

## 11.1 League population

Maintain a private offline population containing:

- current BKG4 champion;
- historical ReCurSiON agents;
- accepted BKG4 ancestors;
- strong public executable agents;
- source-backed top strategies where executable representations exist;
- synthetic mechanic-diverse programs;
- discovered approximate best responses;
- intentionally adversarial specialists that exploit known weak lanes.

Opponent identity is allowed in offline bookkeeping only, never runtime routing.

## 11.2 Payoff matrix

Evaluate exact CUDA W/L/tie payoff matrices across the population.

Track:

- win rate;
- both-seat behavior;
- worst matchup;
- nontransitive cycles;
- strategic response vectors;
- exploitability proxy;
- residual failure clusters.

## 11.3 Approximate best-response search

Continuously search deterministic opponent programs whose objective is to beat the current champion or a league meta-distribution.

A generated adversary does not need to be globally strong to be useful. If it exposes a new hole, it becomes valuable training/red-team evidence.

However, avoid degenerate irrelevant adversaries by using a PAIRED-like regret criterion where appropriate:

prefer challenges where another available strategy can succeed while current BKG4 cannot.

## 11.4 Feedback loop

Every meaningful adversarial loss enters the regret-state archive.

Then:

`new exploiter`
→ `loss cluster`
→ `regret checkpoints`
→ `planner`
→ `macro discovery`
→ `CEGIS`
→ `composition`
→ `new champion`
→ `old champion retained as league member`.

This is the autonomous ratchet toward zero known losses.

Priority mechanics include:

- market-before-town ordering;
- step-0 town demand;
- duplicate-shop demand;

- lockstep market quoting;
- market queue ordering;
- HIRE/BUY_LAND ordering/atomic behavior;

- shed/EOD overflow;
- plant decay vs harvest timing;
- animal care/production timing;
- shop unlock timing;
- end-of-day transitions;
- other exact executable-engine quirks found through source audit.

1. derive the exact executable semantics from source, not stale prose;
2. construct bounded parameterized microstates;
3. enumerate/search alternatives on CUDA;
4. determine whether a dominance rule or robust motif exists;
5. verify whether the advantage is private or merely shared/symmetric;
6. test independent hard cases;
7. distill broad useful rules into Bonsai specialists;
8. reject narrow tape-specific tricks.

This lane may produce rare large step-changes and should remain active throughout the campaign.

# 13. Stage 7 — causal/economic predicate discovery

Routing should evolve from arbitrary threshold fitting toward derived causal predicates.

Candidate derived variables include:

- days/turns until break-even;
- remaining profitable production events;
- expected town/shop demand before next harvest/production;
- shop-demand multiplicity by product;
- market distance to glut floor in units;
- expected added supply before next demand event;
- EOD shed pressure;
- route completion slack before day boundary;
- liquidity after planned hires/land/inventory needs;
- opponent visible production pressure;
- remaining amortization horizon;
- liquidation urgency;
- capital commitment state;
- reversible vs irreversible option value.

The preferred discovery loop is effect-first:

`counterfactual macro effects`
→ `cluster states by effect vector`
→ `search interpretable public predicates explaining clusters`.

This is superior to blindly expanding raw features and hoping a classifier finds a separator.

Do not add new predicates to the runtime registry until they solve actual CEGIS/routing failures or materially simplify multiple specialists.

# 14. Stage 8 — exact/reduced subgame teachers

Certain Kaggriculture subproblems are structured enough to solve more directly than with generic policy mutation.

Prioritize only where loss attribution shows meaningful value.

Potential teachers:

## 14.1 Endgame optimizer

Optimize the final few days when:

- remaining investments have limited amortization;
- shops are known;
- production assets are mostly fixed;
- inventory and market state are known;
- liquidation timing dominates.

Use DP/beam/OR as an offline teacher, then distill decisions into BKG4.

## 14.2 24-turn worker scheduler

Treat each day as a resource-constrained scheduling problem with:

- jobs;
- locations;
- prerequisites;
- deadlines;
- inventory dependencies;
- production consequence;
- EOD constraints.

Do not revert to naive static-distance Hungarian assignment. Existing oracle evidence shows future strategic consequence matters.

## 14.3 Market-order microgame optimizer

Enumerate/order short market sequences under exact shared-market semantics and liquidity constraints.

## 14.4 Production break-even analysis

Derive exact/near-exact rules for when new land, workers, animals, crops, or structures can still amortize before the season ends.

These teachers discover policy. Final execution remains BKG4.

# 15. Edit corpus / BonsaiEditFormer status — paused, preserved, optional accelerator

The corpus and EditFormer infrastructure is **paused**, not deleted and not declared useless.

The pipeline was already hardened and should be preserved.

Do not resume massive corpus generation or 20M-model training simply because infrastructure exists.

## 15.1 Why it is paused

The current evidence says the strategic bottleneck is new capability discovery outside the local edit manifold.

A ranker cannot rank a capability that never enters its candidate pool.

Therefore strategic capability discovery comes first.

## 15.2 When EditFormer becomes valuable again

Resume ranker work if the new synthesizer generates more candidate macros/gates/compositions than exact CUDA can conveniently evaluate.

Then the model should justify itself by measurable improvement such as:

- higher solved loss-regimes per GPU-hour;
- same useful/L→W recall with substantially fewer exact labels;
- higher promotions per exact CUDA budget;
- better acquisition of uncertain/novel candidates;
- reliable prediction of W→L risk or composition conflict.

Potential future outputs should be richer than one scalar score:

- L→W probability;
- W→L risk;
- signed regime-effect vector;
- activation-transfer probability;
- composition conflict;
- uncertainty/disagreement;
- novelty;
- expected value of acquiring an exact label.

If a ranker does not materially accelerate the synthesizer, do not force it into the critical path.

# 16. Validation hierarchy for every strategic promotion

Promotion decisions must optimize Kaggle-relevant outcomes, not cosmetic metrics.

## 16.1 Exact objective hierarchy

1. No runtime/semantic invalidity.
2. No protected W→L.
3. Maximize L→W.
4. Improve worst-strategy/cohort win floor.
5. Improve lower-tail margin robustness.
6. Improve broad useful activation/coverage.
7. Only then optimize average margin.

Do not trade an existing win for a new win somewhere else unless the user explicitly approves such a risk strategy.

## 16.2 Evaluation universe

As appropriate to the stage, preserve coverage across:

- current strong/top strategies;
- historical top strategies;
- strong public executable agents;
- historical ReCurSiON/self-history;
- current champion/ancestors;
- adversarial synthetic league;
- hard known losses;
- fragile wins;
- sealed/independent holdouts.

Do not over-weight raw replay count from one strategy family.

## 16.3 Discovery versus holdout

Maintain clean separation between:

- discovery/search evidence;
- gate/CEGIS counterexamples;
- independent validation;
- sealed final holdout where useful.

A specialist is not validated merely because it perfectly fits the discovery cases that created it.

## 16.4 Both seats

Where the game/setup permits, test both seats. Seat-specific asymmetries must be understood, not ignored.

# 17. Overfitting and legality guardrails

Reject any strategy whose success depends on:

- exact opponent identity;
- exact episode/tape identity;
- exact seed identity as a fingerprint;
- future shop realization not yet observable;
- hidden opponent inventory unavailable legally;
- trajectory-specific exact step/action scripts with no causal regime;
- narrow scalar conjunctions with no independent activation support;
- global application of a specialist known to be mixed-sign.

Timing predicates are allowed when tied to a real mechanic/reveal/deadline/phase transition.

A rule such as “after shop two is visible and remaining horizon is X” can be causal.

A rule such as “at step 156 because case 9 flips there” is not enough by itself.

# 18. Search discipline

## 18.1 Evidence-first

Before new search:

- inspect current champion/lineage;
- inspect prior ledgers;
- identify unresolved hard cases;
- identify whether the missing piece is search control, representation, routing, composition, or actual absent strategic headroom.

Do not rediscover terminally rejected ideas.

## 18.2 Bounded escalation

Search progression:

`small informative probe`
→ inspect
→ expand only promising basin
→ transfer test
→ causal diagnosis
→ synthesize.

Never launch enormous blind grids merely because CUDA is fast.

## 18.3 Record serious experiments

For every material experiment record:

- target loss/regime;
- parent identity;
- checkpoint;
- horizon;
- search family;
- candidate count;
- exact CUDA games;
- fault count;
- baseline result;
- best result;
- L→W/W→L;
- margin delta;
- strategic motif;
- transfer evidence;
- rejection/acceptance reason.

Permanent compact evidence belongs in the experiment ledger; large raw artifacts remain in ignored scratch.
